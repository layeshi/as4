# 法律语义升级与执行故障恢复

本次更新不迁移已有世界，也不重建、改写法律或补发资源。第一纪和缺少 `lawSemantics.version` 的第二纪继续使用历史行为。新版第二纪创世将法律语义 2 写入原始 genesis；它独立于法律计算 VM 版本，适用于全部第二纪 premise。

## 显式升级

1. 正常备份世界目录（快照、命令日志、事件日志）及账户和运行器配置。
2. 管理员通过登录会话或 `X-Admin-Key` 查询 `GET /api/admin/law-semantics`。响应只含版本、脱敏保护状态和 open 重订的 ID/到期刻。
3. 使用 `X-Admin-Key` 调用 `POST /api/admin/law-semantics`，JSON 为 `{"version":2}`。有 open 重订时返回 `open_refounds` 和 `refounds:[{id,expiresTick}]`，世界不升级；等待重订自然完成后重试，不要手动推进时间绕过条件。
4. 检查返回 `version:2`、公开状态 `world.lawSemanticsVersion:2`，并执行现有 replay 工具核对快照。升级请求本身已使用持久回执，跨升级快照的尾部恢复与从原始 genesis 的全回放使用同一记录。

升级不自动启用法律计算 VM2，不重写已有法律、提案 spec/voters 或历史门槛。VM2 的容量迁移仍走现有 `/api/admin/law-execution`。

## 两种保护暂停

- **容量保护**：`ruleExecution.protection` / `law_execution_capacity`。检查 `/api/admin/law-execution` 的预检和容量需求；合法扩容后使用普通恢复入口。
- **执行故障保护**：`lawSemantics.protection` / `law_execution_fault`。未知引擎异常撤销整条请求：之前成功的动作、随机数、收件、唤醒、账本与刻推进一起回滚；只保留命令进度、公开故障事件与暂停。普通 `resume` 和容量配置都不能清除此保护。

普通业务失败只撤销失败动作；请求中之前成功的动作保留。before 法律求值错误是动作拒绝，不会触发全城保护。

公开概览、模型感知 `now.lawProtection`、SSE tick 和管理员实验面板显示故障命令编号、命令类型和固定 `engine_exception` 码。暂停期间禁止普通世界写入，包括注册、领养、家书、天气投票、动作、tick 和管理员余额调整。查询仍可用；受控维护仅允许 `pause`、`law_execution`、`redact`、`reset_owner_key`、`backstage` 以及 `law_recover`。维护操作也使用原子边界及持久回执。

## 诊断与验证恢复

命令编号可在私有 `commands.jsonl` 中定位原请求。快照的 `lawSemantics.failedCommand` 也保存私有请求副本。两者可能包含独白、私密动作和认证哈希，不能发布到公开页面或工单。公开诊断不保存异常消息/堆栈，以免引擎错误文本带出私密内容。

修复程序并完成测试后，在管理员实验面板点击“验证修复并恢复”，或调用 `POST /api/admin/law-recover`，JSON `{}`。接口支持管理员登录会话及 `X-Admin-Key`；会话写入须使用既有 `X-Houren-Request: 1` 防跨站机制。

验证在当前世界的隔离副本上运行原失败请求，检查当前容量、引擎执行和执行后的容量。验证的全部效果都丢弃：不会重复注册/领养、扣费、发送收件或推进 tick。

- 仍有未知引擎异常：返回 `paused`，reason 为 `law_execution_fault`，保留原保护。
- 容量检查失败：返回 `paused`，reason 为 `law_execution_capacity`，原执行故障保护也保留；调整容量后再次显式验证。
- 验证成功：返回 `{"ok":true,"paused":false,"probe":"success","resubmitted":false}`。
- 原请求现在得到预期业务失败（含 act 的内部失败结果）：返回 `probe:"business_failure"`，明确表示未成功执行原业务，同样不补交。

恢复后运行器按最新启用开关恢复，居民重新感知后重新提交，tick 由正常调度推进。不要重放故障请求作为补交操作。恢复结果也有持久回执，日后程序再次变化不会改写历史验证结论。

## 回执与崩溃边界

法律语义 2 的每条请求（包括成功、业务失败、容量失败、程序故障、保护期间拒绝和恢复）先在内存隔离副本完成，生成请求、结果、事件、唤醒以及持久世界状态差量。日志一行是 `command-receipt-v1` 帧，包含 SHA-256 校验和，换行是完整帧终止符。写完文件并 fsync 文件及父目录后，才提交业务状态、发控制事件、发布事件/唤醒或写快照。

- 追加前崩溃：没有可见业务变化，也没有新历史命令。
- 追加中断：最后一行不完整（即使缺少的只有换行）在全回放和启动修复中均丢弃；之后从上一个完整回执继续。
- 完整追加后、提交前崩溃：启动从旧快照应用完整回执，执行结果只应用一次；不重新调用处理器。
- 提交后、事件/快照期间崩溃：快照的 commandN 决定尾部范围；事件存储先截到该快照序号，再从回执重建。
- 写入或 fsync 报错：运行时 fail-stop，拒绝后续命令并停止托管循环；不能在不确定追加结果的进程里继续。重启通过完整帧界定历史，完整追加可能存在，所以操作者先查询结果再重试。
- 完整帧校验失败、中间坏行或差量的源状态哈希不匹配：拒绝恢复，检查备份与代码版本，不能忽略错误强行继续。结果哈希也必须匹配。

旧 JSON 请求行仍可读取并按旧语义执行。原始 genesis 和旧命令不从当前语义版本反推。快照和日志为私有恢复数据；HTTP 返回不包含回执差量。

状态差量替换变化数组、递归记录变化对象，较每命令完整快照节省空间，但事件和变化数组可能仍较大。每命令克隆、状态哈希及同步 fsync 有额外 CPU/I/O 成本，应监测日志体积与延迟；本次不宣称新的吞吐保证。隐藏事件/唤醒由回执单独记录，启动恢复静默重建事件而不重复通知运行器；临时计算表、费用托管、规则结算标记不进入快照，沙盘统计只在在线提交时保留，不是持久世界状态。
