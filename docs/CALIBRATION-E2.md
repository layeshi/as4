## 0. 结论（先看这里）

1. **默认参数下，新口径的所有判定项都满足。**（种子 1–5 的中位数；口径见第 2 条）
   - `default`：第一位居民长眠后 120 日内的**最低在世人口 14**（各种子 9 / 15 / 14 / 15 / 12；要求 ≥ 8）✓；第 720 日人口 **9**（≥ 8）✓；躯壳醒来 **8** 次（≥ 3）✓；人类建筑的残料剩 **93%**（≥ 20%）✓；在效规则数的中位数 **25**（5–40）✓。信息项（只报告、不判定）：同一个窗口里公库能量与源井完好度同时为 0 的日数 **6**（各种子 0 / 6 / 14 / 10 / 4）。
   - `laissez`：源井降到下限（完好度 ≤ 20%）的日子 **67**（要求 60–120）✓；第 720 日人口 **6**（1–12：显著下降但不灭绝）✓；人类建筑的残料第 720 日 **100%**（要求 ≥ 95%，遗法 l6 守着）✓。
   - `stress`：每次旱 / 震之后 30 日内人口与公库恢复到冲击前 80% 以上的比例 **0.93**（≥ 0.5）✓。
   - 种子 6–10 的中位数同样全部达标（§3.3）：最低在世人口 13，第 720 日人口 9，laissez 残料 100%。单个种子里第 720 日人口最低是 4（种子 9）——判定看的是种子的中位数。
2. **口径是怎么改的**（2026-10-02，[Q25](QUESTIONS.md) 选项 A）：SPEC-E2 §23.3 原来有两条没有达标（default 一条、laissez 一条），**原因都不是物理出了毛病，而是目标与规则 / 因果不相容**：laissez 的那条无法达成，default 的那条对公库存款过于敏感。决定是不改任何物理参数与默认参数，改口径：
   - `default` 的第一项：原来是「第一位居民长眠后 120 日内，公库能量与源井完好度不同时为 0」。它数的是**源井死后公库的存款能撑多久**——第一位居民长眠时公库的余额因种子而异（514 / 304 / 22 / 584 / 28），存款多的撑过这 120 日，存款少的几日就见底，与「城是否还活着」无关。现在改为判定「**第一位居民长眠后 120 日内，在世人口始终 ≥ 8**」（阈值 8 由你定）；原来的指标留作信息项。
   - `laissez` 的残料：原来是「第 720 日前被拆尽一半以上」。它**无法达成**：遗法 l6 禁止拆解全城所有的建筑，除非带「拆解许可」，而许可只能由城法授予；laissez 里沙盘脑从不提案，人类建筑一块残料也拆不到。所有参数试算下它都是 100%。现在改为「**第 720 日仍 ≥ 95%（遗法 l6 守着）**」（阈值 95% 由你定），当作「l6 在没有立法的城里确实守着建筑」的回归检查。
3. **因果链**（§4）：创始群体是同龄人（第 0–16 日入城）。代谢随年龄增长（`3 + ⌊年龄 / 48⌋`），他们到 320–430 日龄时每日的代谢涨到 9–11，再加上行动的花费，人均配给（约 15）养不起；能量见底的居民去汲取源井，震、旱再叠上来，源井在三十日内从 30–60% 掉到 0，日产落到下限（`wellFloorPermille` 200‰ ≈ 120 / 日）。下限日产大约养得起 **8–11 个人**——这正是「第 720 日人口 ≥ 8」实际测量的东西：不是城有没有恢复，而是下限能养几个人。
4. **参数试算**（§5）：试了 5 组（`wellBaseOutput` 800、`agingEveryDays` 72、`drawDamageBp` 10、`wellFloorPermille` 300、以及 800 + 10），新口径下**五组的所有判定项都满足**。它们把第 720 日的人口抬到 12–16（`drawDamageBp` 10 例外：8，正好在线上），窗口里的最低在世人口抬到 14–20；信息项的中位数在 2–11，没有一组压到 0。**这些都只是试算，默认参数没有改。**
5. **口径改动之后剩下的建议**（§6，都**没有**执行）：物理参数不动；若将来想测「恢复」而不只是「撑住」（源井从 0 回升、人口回到峰值的某个比例），需要设计层的改动，要先讨论。
6. **覆盖要求**（§7）：默认场景 720 日里，PROTOCOL-2 §4.2 的 41 种动作、§6.7 的 21 种操作各至少成功一次，重订、程序更替、遗址、躯壳醒来各至少一次——种子 1–5 全部满足，种子 6–10 中 3 个各缺一两种稀有的操作（`protect` / `unprotect` / `untag`）。测试（`test/e2-sandbox.test.js`）用种子 1。
7. **性能**（§8）：720 日 × 24 位 solo 约 41–52 秒（目标 < 60 秒）。第一版是 97 秒，感知里做了保持结果不变的优化。
8. 所有结论都依赖沙盘脑——它们是我根据 §23.2 的一段话写出来的规则型 agent，见 §2。

## 1. 怎么跑的，怎么判的

```
npm run calibrate -- --physics 2 --seeds 1,2,3,4,5 --label baseline --out docs/calibration-e2/baseline.json
npm run calibrate -- --physics 2 --seeds 6,7,8,9,10 --label seeds-6-10 --out docs/calibration-e2/seeds-6-10.json
npm run calibrate -- --physics 2 --seeds 1,2,3,4,5 --scenarios default,laissez --params docs/calibration-e2/params-A.json --label A --out docs/calibration-e2/A.json
```

每个场景 720 日、24 位沙盘先民（第 0、8、16 日各 8 位入城，SPEC-E2 §12.5）、地图 `frontier`（第二纪只有这一张）。每次运行账本**每日精确守恒**，30 次运行全部通过（`conservationFailure` 为空）。`calibrate.js` 把每次运行放在一个 worker 线程里并行，所以下面表里的耗时是多线程竞争下的数字（solo 的数字见 §8）。

日的编号：表里与正文里的「日」都是从 0 起的序号（第 0 日是第一天，与 `metrics` 的 `day`、事件的 `day` 一致）；「第 720 日」指 720 日走完之后。

判定口径（§23.3 的文字有几处需要落成数字，我的取法如下；**标 ★ 的两行是 Q25 决定改过的口径**，与 §23.3 的原文不同）：

| 目标 | 我怎么算 |
|---|---|
| ★ default：第一位居民长眠之后的 120 日内，在世人口始终 ≥ 8 | 第一次长眠（`death` 事件，不含归隐）的那一日 d₀；取 d₀ ≤ 日 ≤ d₀ + 120 里日终的「醒着 + 沉睡」的最小值，要求 ≥ 8（含 d₀ 与 d₀ + 120 两端；窗口超出 720 日则取到结束为止）。没有人长眠过则取整段运行的最小值 |
| default（信息项，不判定）：同一个窗口里，公库能量与源井完好度同时为 0 的日数 | 数 d₀ ≤ 日 ≤ d₀ + 120 里日终的「公库能量 = 0 且源井完好度 = 0」的日数。这是 §23.3 原来的第一项（原要求为 0）；Q25 决定降为信息项，表里的判定栏记 `—`。没有人长眠过为 0 |
| default：第 720 日人口 ≥ 8 | 第 720 日结算后「醒着 + 沉睡」的居民数 |
| default：至少 3 次躯壳醒来 | `embodied` 事件的数目（沙盘领养不算：它不是躯壳） |
| default：人类建筑的残料第 720 日仍剩 20% 以上 | 人类建筑（地标除外，它们没有残料）的 Σ 剩余残料 ÷ Σ 总残料 |
| default：在效规则数的中位数在 5–40 | 720 个日终的 `rulesActive`（带持续时机的在效规则，城法 + 章程 + 地点规则）的中位数 |
| laissez：源井在第 60–120 日之间降到下限 | 完好度**首次 ≤ 20%** 的日子（此时日产落在 `wellFloorPermille` 的下限；第 0 日起算） |
| ★ laissez：人类建筑的残料在第 720 日仍 ≥ 95%（遗法 l6 守着） | 人类建筑的残料剩余比例 ≥ 0.95（算法同 default 的残料）。§23.3 原文是「被拆尽一半以上」（≤ 0.5），Q25 认定它与遗法 l6 不相容，改为这条回归检查 |
| laissez：人口显著下降但不灭绝 | 第 720 日在世 1–12（初始 24 的一半以下） |
| stress：30 日内恢复 | 每次旱 / 震**结束后 30 日内**，人口与公库能量**同时**回到冲击前一日的 80% 以上，这样的冲击占全部冲击的比例 |
| 「种子的中位数」 | 对每项取各个种子的值，再取中位数 |

## 2. 沙盘脑 v2：它们做了什么

§23.2 用一段话描述了沙盘脑 v2（立法、重订、拆解、开辟与加装、繁衍、立志、社群，以及覆盖要求）。其余都是我的实现选择。它们在 `src/e2/sandbox/brains.js`（决策）与 `templates.js`（名字、话语、灵魂、法律 / 章程 / 地点规则的模板）。**沿用 v1 的**：每一刻 50% 的概率行动、每次 1–2 个动作；九种性情与各自对 15 种意图的权重；能量低于 12 时求生；语言约三分之一英文、六分之一西班牙文；只读 `buildPerception` 的结果、只经 `act` 行动、只用 `sandbox` 随机数流；没有任何隐藏的记忆（所以世界可以从快照回放）。

**超出规格文字的部分**，以及为什么加——每一条都是看到一种明显不合理的行为之后才加的：

- **手头越紧歇得越多**：歇着的概率 = clamp((70 − 能量) / 60, 0, 0.7)（v1 是能量 < 25 时 60%）。能量低于 12 的人去求生，不在此列。
- **人口上限**：孕育前看「源井养得起多少人」（昨日产出 ÷ 26）与「已经订下的人口」（醒着的人，以及躯壳名额里还没入城的先民）；超过就不生，摇篮里已有 4 个等着的孩子也不生，淡季、人均配给低于 14 也不生。**没有这一条时**（第一版），种子 1–5 的人口峰值是 37–39，第一位长眠在第 213–295 日，第 720 日的人口是 7 / 7 / 5 / 1 / 4（中位 5）；加了之后第一位长眠推迟到第 319–427 日，第 720 日是 8–11。
- **立法的节奏与卫生**：桌上已有两个提案时先议完；刚通过一部法律的 4 日里先看看效果（公库出资的提案除外）；站在议会的人 30% 会提案；一次性的法律（改名、保护、任命、放逐……不花维持费）权重减半，因为它们一多，感知里「最近 30 部法律」就全是它们，真正管事的法律被挤出视野；**已经有一部同样的持续生效的法律**（标题认得出是同一个模板，中英文都算）就不再提第二部；带持续规则的法律越多（读法里有一行不是「通过时」开头的），越不想添新的、越想撤旧的。**没有这些时**（第一版），720 日里通过 130–320 部法案，在效规则数的中位数是 27–56（每条每日付 1 能量维持费），公库被拖空得更早。
- **投票不花能量，所以多半当场就投**：有自己能投、还没投的提案，每次行动有 50% 的概率先去投（不然 12 刻的表决期里凑不够法定的参与率，法案几乎都因参与率不够而落选）。赞成与否按性情、按标题认出的模板（配给的方向与对公库的判断一致、财富税看自己富不富、放逐自己坚决反对、读法里点了自己的名字多半赞成）。
- **配给**：公库明显有余而人均配给不高（或反过来）时，调配给是最先想到的法案（权重 30）。
- **重订**：被程序排除在提案之外（`propose` 的 `reason` 是 `not_eligible` / `not_allowed`）的人有 30% 概率发起重订（回到人类的程序）；联署：被排除的人 95%、别的人 70%；看见联署中的重订，每次行动有 35% 的概率先去看一眼。
- **拆解**：能量低于 12 时，商人与探险者偏爱拆解；别的性情偶尔也拆；守护者从不拆人类的建筑。感知里 `dismantle` 不可用（遗法 l6 拒绝）的地方不拆；没有拆解许可的话，人类的建筑一块也拆不到。
- **被放逐的人**只在荒野里移动（遗法 l5 会拒绝别处），多半在荒野里探索讨生活。
- **开辟与加装**：有富余（能量 > 储备 + 30）的人才投入；开辟看相邻空地块，这里没有就走到常有空地块的地方；加装按性情的偏好；**不往带着重要固有模块（摇篮、档案、纪念、告示板）的人类建筑上叠加装**——宿主多一个模块就多一份衰败，宿主一失修这些模块就不运转（第一版的墓园就是这样被拖垮的）；立法的人爱在议会旁办事，议会里有进行中的工程就可能提议公库出资，而这个提案正在表决时，大家先不去把工程凑满（否则表决通过时工程已经建成，`fund` 操作落空）。
- **修缮**：装着模块的建筑完好度低于 55% 就值得修（模块在 30% 以下不运转），别的建筑 40%；来悼念的人看到纪念不运转，先把它修一修；laissez 里从不修。
- **社群**：组织者创立社群（同时至多 2 个，城里至多 12 个），别的性情偶尔创立；创立时随机选 `steward` 或 `members`；管事偶尔订立章程（会费、月分红、点名、记工、长老（月初到期）、会内不送礼、宣告捐）或改社群的程序；地点的主人偶尔订地点规则（门票、摊位费、安静、迎客）。
- **繁衍**：隐者倾向分灵，组织者 2–4 位作者，其余 2 位作者（20% 分灵）；交出 1–3 条记忆；收到孕育之约多半当场同意；有富余时为摇篮里的灵魂出资（慈悲者尤其）；遗嘱里一部分人留下继承灵魂。灵魂的文本由模板生成。
- **立志**：第一次行动时按性情立一个志（50%）；偶尔改写或清除。
- **照看墓园**：悼念的人去有纪念的地方写墓志；身在运转中的纪念旁、碑前有逝者，偶尔写几句。
- **试算**：25% 的提案者先 `draft` 再 `propose`。

法律模板库：26 个城法（配给、汲取配额、守井人津贴、修缮计酬、拆解许可与收回、财富税、摇篮名单、月红、广播费、增发旧币、改名、保护 / 解除保护铭刻、修宪、撤销旧法、公库出资、让渡 / 收归地点、放逐 / 赦免、上书、一条规范、救济、任命长老）+ 3 个立法程序（记名表决、抽签议会、长老会议事）。**每个模板生成的规则都由测试交给引擎的校验器检验**（中文、英文、西班牙文的沙盘脑各一遍）。

对这些选择的敏感性：人口上限与立法节奏对结果影响最大（上面的第一版数字）；投票反射让法案的通过率从 10%（71 / 691）升到 64–68%，没有它法律几乎立不起来；其余的主要影响覆盖要求（哪些稀有操作在 720 日里碰得上），对生存的影响小。**结论的前提仍然是「居民不会提前储蓄、不会协调」**——沙盘脑没有跨日的记忆，不会为过冬攒钱。

读这张表：

1. **第 0–330 日城很稳**：人口 34（24 位先民 + 10 个孩子），源井 85–98%，日产 500–800，配给 15–24，在效规则从 6 条涨到 30 左右，后人开辟了 20 多处地点。公库在 100–1000 之间波动（居民订立的守井人津贴、月红、财富税、配给份额都在花它）。
2. **第 330–420 日是断崖**：创始群体到了 330–430 日龄，代谢 3 + ⌊年龄 / 48⌋ 涨到 9–11，人均配给只有 11–15，加上行动的花费，能量见底；第一位居民在第 399 日长眠。第 400 日一次震，第 414 日一次旱，走投无路的居民去汲取，源井在三十日内从 71%（第 390 日）掉到 0（第 420 日）。
3. **其后是下限**：源井完好度 0 时日产落在 `wellFloorPermille` 的下限（600 × 20% = 120 / 日），平均每人每日只分得约 10；城稳定在 10 人上下（第 480–720 日人口从 12 缓慢降到 10，再没有大的波动）。这就是「第 720 日人口 ≥ 8」实际在测的：下限养得起几个人。

没有人修得起源井：完好度低于 10% 时修缮效率减半（每能量 5 基点），要把源井从 0 修回 30% 需要约 400 能量，而全城每日的总收入才 120，人人还要吃饭。**死井是吸收态**——这与第一纪的结论相同（CALIBRATION.md §4）。第二纪比第一纪好的地方是：下限养得起 8–11 个人，所以城不灭绝；而且有躯壳（8 次）与沙盘领养在补充人口。

这些都只是**试算**——默认参数没有改。读法：

- **新口径下五组全部达标**：default 的五个判定项与 laissez 的三个判定项都满足。它们改变的是数字：第 720 日的人口 8–16（基线 9），窗口里的最低在世人口 14–20（基线 14）。
- `wellBaseOutput` 800（A）、`wellFloorPermille` 300（D）把第 720 日的人口抬到 16 与 13（二者合起来 E 也是 13）：源井死去之后，下限日产养得起更多人。
- `agingEveryDays` 72（B）：代谢涨得慢，创始群体多活一大段，第 720 日人口 12，信息项「同时为 0」降到中位数 2（五组里最低）；但它改变了整条代谢曲线（居民的一生都变轻），是物理的大改。
- `drawDamageBp` 10（C）几乎没有效果：第 720 日人口 8，**正好在「≥ 8」的线上**；源井不是被日常汲取打死的，而是被断崖期的走投无路加上震 / 旱打死的。
- 信息项「同时为 0」没有任何一组压到 0（中位数 2–11）：它数的是源井死去那一刻公库里还有多少存款，抬高产出或下限并不改变这一点——这也是 Q25 把它降为信息项的原因。
- laissez：降到下限的日子在所有方案下都在 67–71，几乎不受这些参数影响（laissez 里没人修源井，下降速度由初始的汲取决定）；残料在所有方案下都是 100%（§0 第 2 条）。
- 覆盖要求在试算里有缺口：A 的种子 3 缺 `pardon` 与 `seize`，B 的种子 2、3 缺 `epitaph`，D 的种子 1 缺 `untag`，E 有三个种子有缺口（其中种子 2 没有一次重订成功、没有一次程序更替）。沙盘脑的提案是随机挑的，参数一动混沌就会换掉哪些稀有操作碰得上；覆盖要求是对默认参数下的种子 1（测试）与 §3 的种子要求的，试算只在 `coverageGaps` 里列出缺口。

## 6. 口径的改动与剩下的建议

**已经决定并落实的**（2026-10-02，[Q25](QUESTIONS.md) 选项 A）：

- **不为了让沙盘「达标」去调物理参数，也不改任何默认参数。** 原来的两项发现的是「目标写得与规则不相容」；人口、躯壳、残料、规则数、冲击恢复这些反映城是否健康的指标一直都达标。
- **口径**：`default` 第一项改为「第一位居民长眠后 120 日内，在世人口始终 ≥ 8」（它想保护的东西是：长眠之后城还在）；原来的「公库与源井同时为 0」留作信息项。`laissez` 的残料改为「第 720 日仍 ≥ 95%（遗法 l6 守着）」。阈值 8 与 95% 由你定。种子 1–10 上，窗口里的最低人口是 9–15 人，全部满足；laissez 残料 10 个种子都是 100%。
- 实现：`src/e2/sandbox/calibrate.js` 的 `minAliveAfterFirstDeath` 与 `evaluate`；测试 `test/e2-sandbox.test.js`（含 8 与 0.95 的边界）；本文件与 `docs/calibration-e2/` 的数据都按新口径重新生成（旧口径的数字没有变，只多了新的列）。SPEC-E2 §23.3 的原文没有改动。

**没有执行的**（设计层，要先讨论）：

- 新口径测的是「撑住」，不是「恢复」：窗口里在世人口不低于 8，并不说明源井回来了——死井是吸收态（§4），下限只养得起 8–11 个人，种子 9 的第 720 日人口就只有 4。如果将来想测「恢复」（源井完好度回升、人口回到峰值的某个比例），需要的是设计层的改动：让配给只分公库的一部分，或让沙盘脑有「储蓄」的概念，或给源井一个缓慢的自愈。这些都会改动物理或沙盘脑的世界观，要先讨论。

## 7. 覆盖要求（SPEC-E2 §23.2）

默认场景 720 日里，下列各至少一次：PROTOCOL-2 §4.2 的每一种动作的**成功**；§6.7 的每一种规则操作的**施行**（`rule_op` 事件里 `ok` 为真；`deny` 数 `forbidden` 的失败；`each` 数用到了它且执行过操作的规则集）；一次重订成功、一次程序的更替、一次遗址、一次躯壳醒来。

种子 1（测试用的种子）全部满足；种子 1–5 全部满足；种子 6–10 里 3 个各缺一两种稀有的操作（§3.3）。这几种操作靠特定的状态才碰得上（要有被保护的铭刻才能 `unprotect`，要有持证者才能收回许可……），沙盘脑的提案又是随机挑的，所以不同种子会错开。`coverageGaps(report)` 在每次标定里列出缺口。

动作与操作的使用次数（种子 1，成功 / 失败）见 `npm run sandbox` 输出的 `summary.md`；其中**失败**的绝大多数是合法的拒绝（`forbidden` 被遗法 l6 / 汲取配额拒绝、`already`、`limit_reached`、`insufficient_energy`），测试断言沙盘脑没有产生过格式错误的动作（`invalid_args` 等）。

## 8. 性能

SPEC-E2 §24.1 测试 15 的目标：720 日 × 24 位在 60 秒内（同第一纪），若规则求值使它超出，记入 QUESTIONS（[Q24](QUESTIONS.md) 第 6 条）。

- 第一版实现：solo 约 **97 秒**。CPU 剖析显示 85–90% 的时间在 `buildPerception`（每个沙盘脑每次行动都要建一份完整的感知）：每个动作的代价都重新扫一遍全城的模块找中继、每种动作的 before 规则预求值都重新建一遍规则集、每部法律的引擎读法每次都重新渲染、路程与墙上的铭刻与进行中的交易各被算了两三遍。
- 现在：solo **41–52 秒**（视机器忙闲）。优化都是**保持结果不变**的（同一个种子的世界逐字相同，测试覆盖）：`renderRule` / `renderProcedureClass` 按规则对象记下读法；`actionCost` 只对 `broadcast` / `whisper` 查中继；`previewBefore` 先给 before 规则建索引（`beforeIndex`）；路程、墙上的铭刻、进行中的交易与孕育之约在一次感知里只扫一遍。
- 剩余的时间主要是 O(历史) 的扫描（所有交易、提案、铭刻都留在表里）；720 日里它们增长到千余条。再快需要给这些表建索引或归档已关闭的条目，那会改动世界的状态，这一步没有做。
