# 在线计算资源适配

正常运行 `node server.js` 或 `npm start` 时，服务自动探测实际可用 CPU 和内存。当前法律语义 2 的世界使用常驻计算线程，有序准备世界命令，由主线程持久化回执并发布已提交状态；历史查询、导出和管理员快照的重型计算使用独立后台池。第一纪及其他旧语义世界保留内联执行，后台池仍可使用。

独立计算可同时使用多个核心；同一世界的动作顺序、三城结算、随机流与账本继续按既有规则执行。模型请求并发、行动频率、费用预算以及居民程序的单次隔离限额分别配置。

## 默认预算

有效 CPU 同时考虑进程 affinity、Linux cgroup v1/v2 及祖先配额、管理员上限。小数 CPU 配额保留为小数；计算槽位按整数核心数扣除至少 1 核、约 1/8 的余量。例：2/8/16/64 核分别最多使用 1/7/14/56 个计算槽位，世界计算也占用槽位。

有效内存取物理内存、可识别系统或容器约束、管理员上限的最小值，默认服务软预算为其中的 75%。主进程与所有工作线程共享进程 RSS，统一记账；任务预留还考虑候选副本、结果、后台线程启动和居民程序子进程。缓存按有效载荷字节淘汰，默认上限为服务预算的 10% 与 4 GiB 的较小值，使用 Buffer 保存内容并限制条目数。

有任务时按 CPU 与内存双重准入派发，任务数、队列负载和等待时间均有界。世界命令优先；单计算槽位下，正在运行的纯后台任务可中断并重新排队。后台任务的总生命周期有上限，不能无限重试。资源紧张时清理缓存、回收空闲后台线程并暂缓新任务；查询过大时提示缩小日期范围，不返回不完整的历史作为完整结果。

软预算用于准入和降载，不能等同于操作系统强制的进程内存限制。需要严格隔离时，结合部署环境的 cgroup、服务进程限制或 Windows 作业限制。

## 手动配置

以下环境变量重启生效；省略时使用自动值：

| 变量 | 单位 / 值 | 含义 |
| --- | --- | --- |
| `RESOURCE_CPU_LIMIT` | 正数，可为小数 | 有效 CPU 上限，不能扩大实际可用的 CPU |
| `RESOURCE_MEMORY_MB` | 正整数，MiB | 有效内存上限，服务软预算再取其 75% |
| `COMPUTE_WORKERS` | 正整数 | 总计算槽位上限，包含世界线程 |
| `COMPUTE_CACHE_MB` | 非负整数，MiB | 缓存载荷字节上限，0 关闭缓存 |
| `COMPUTE_QUEUE_LIMIT` | 正整数，默认 256 | 世界队列和后台队列各自的任务数上限 |
| `WORLD_EXECUTION_MODE` | `auto` / `worker` / `inline` | 默认 auto；兼容旧语义时使用 inline。auto 启动线程失败可在尚未执行在线命令时回退 inline |

Linux 示例：

```sh
RESOURCE_CPU_LIMIT=8 RESOURCE_MEMORY_MB=8192 COMPUTE_WORKERS=4 COMPUTE_CACHE_MB=512 npm start
```

Windows PowerShell 示例：

```powershell
$env:RESOURCE_CPU_LIMIT = '8'
$env:RESOURCE_MEMORY_MB = '8192'
$env:COMPUTE_WORKERS = '4'
$env:COMPUTE_CACHE_MB = '512'
npm start
```

Node ≥20 保持兼容；缺少部分资源 API 时使用能力检测与回退。Linux 读取真实 cgroup 挂载与成员路径，按祖先最严格限制处理；同时读取 CPU affinity，避免新版 Node 将小数配额取整后丢失有效配额信息。Windows 普通主机自动识别系统资源，未识别的 Job Object 内存限制及超过 64 逻辑核的特殊情况需要显式上限，并在状态中标识约束未知。

## 查看生效状态

管理员「服务器状态」增加计算资源卡片，显示生效模式、有效 CPU、槽位、内存预算、实际 RSS、预留、缓存、队列、降载原因以及主线程、世界线程与后台线程实际 V8 堆上限。后台线程按需启动，空闲时可能尚未分配。

同样的数据可从已登录管理员的 `GET /api/admin/server-status` 中的 `compute` 字段读取。运行器及模型密钥、居民私人输入和文件路径不进入资源状态。

V8 堆与整体内存预算是不同限制。现有 Node 启动参数继续生效；父进程的 `--max-old-space-size` 会覆盖 Worker 声明的旧生代上限，因此状态显示实际堆上限，而非仅显示声明值。后台缓存使用原生 Buffer，但主线程的世界镜像仍受其自身 V8 堆上限约束；超大单世界可在部署配置中显式调整 Node 堆，同时核对服务总预算。

## 提交与故障

世界计算线程不直接写命令日志；主线程在持久化前重新核验账号、管理权、令牌和前置版本。回执落盘后才确认世界提交、更新只读镜像和发布事件。取消或撤权发生在落盘前时，丢弃候选；已落盘回执不因超时重新执行。

唤醒、查看及行动的会话更新使用每个世界的有界顺序队列，内容在当前已提交版本上生成和计量。模型网络请求在队列之外；排队超过 30 秒的请求不会随后执行或收费。批量唤醒的版本衔接及旧代币附加计费行为见 [修复说明](fixes/2026-10-27-batched-session-admission.md)。

托管客户端对明确的计算繁忙最多尝试 4 次，退避和重试起始窗口有界，并核验原感知的 tick 与提交权限。最终繁忙不消费下一刻的初始唤醒机会，也不额外调用模型或重复已提交动作。详见 [背压处理说明](fixes/2026-10-27-managed-compute-backpressure.md)。

线程异常、提交确认丢失或持久化不明时，停止新的世界写入。正常重启通过既有快照和回执恢复；居民程序的已记录结果不重新运行。故障期间保留只读诊断，不能用同时启动第二个进程写同一世界目录来恢复服务。

事件恢复逐条读取日志，保留有界窗口，不再为整个历史创建多份全文副本。管理员快照固定在同一命令边界，后台只读取对应的日志字节前缀；新命令可以在捕获完成后继续执行。

## 验证与性能复现

```sh
node --test test/adaptive-compute.test.js test/event-memory.test.js
node scripts/online-compute-benchmark.mjs legacy 20000
node scripts/online-compute-benchmark.mjs worker 20000
```

性能脚本只创建临时合成世界，在随机本机端口运行 HTTP，并在完成后删除临时数据；不读取部署数据，不调用模型。在线阶段使用 12 位合成居民、指定数量的旧账目、24 条固定 tick 和并发状态查询，暂停自主服务以固定输入序列。后台阶段使用独立的合成历史载荷生成 12 份相同 ZIP。比较时保持 Node、数据和实际 CPU/内存配额相同，核对最终世界哈希，并单独记录扩核收益和单命令开销。
