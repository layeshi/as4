# 用类型化动作工具减少模型参数负担（设计草案）

状态：未实施。基于运行审计的生产版本c9bbe61和其工具循环；与规则计算预算机制独立。目标是居民仍决定行动、对象、金额、文字和法律内容，平台承担接口编码、校验、实体引用与工具控制的机械负担。

## 方案选择

推荐把外层act.actions中的业务动作提升为独立工具，由平台适配成原引擎动作。单一act配oneOf等分支schema可保留批处理，但仍要求模型编写type和嵌套载荷，不同供应商对子集支持不同；只增加提示和错误例子不能从机制上杜绝不合法结构。

第二层可提供实体选择句柄，适用于多种ID容易混淆的场景。暂不增加自动修正模型文本或由平台代选行动的机制。原生schema约束不被支持时仍有模型输入格式失败可能，不能承诺所有模型都会产生有效调用。

## 工具与引擎适配

例：

| 新工具 | 模型填写 | 适配层生成 |
|---|---|---|
| read_law | law_id | type=read、law=law_id |
| read_document | document_id | type=read、doc=document_id |
| say | text | type=say、text=text |
| whisper | resident_id、text | type=whisper、to=resident_id、text=text |
| move | place_id | type=move、to=place_id |
| done | 空对象 | 结束当前醒来，不生成世界动作 |
| look_law | law_id | 使用免费查看路径，不生成read动作 |

模型不再填写actions数组、type，也不用记住结束标记必须放在act外层。read_law与look_law有明确的不同作用和原有费用/地点规则，不能通过适配绕过read的业务限制。独白使用明确的工具参数或独立think接口，保持原来的私人性与现有计费语义，具体工具划分在实现时核对。

复杂动作draft/propose仍由居民提供法律内容；其JSON结构也由结构化参数定义表达。类型化工具只解决协议负担，不能替代居民的政策设计与判断。

## 统一动作定义

现有src/e2/lore/actions.js已包含字段和粗略类型，但缺必填、可选、互斥、范围与长度等完整信息。扩展一个规范定义，包含工具名、引擎字段映射、字段类型、必填条件、枚举、引用类别、文本长度及整数范围。

从同一规范生成工具schema、入参校验、文档例子和错误说明。保持与真实引擎校验一致；动态业务约束（资金、地点、法律否决、资格等）留给引擎。不能把两种“正确性”合并。

按明确供应商能力生成适用schema；严格约束模式需在线路能力确认后才启用，不能给所有兼容接口盲目添加同一strict参数，也不能自动付费探测。未知线路默认声明未确认，通过统一服务端验证守住执行边界。

## 实体引用

工具参数按用途区分law_id、resident_id、place_id等。对当前可见且大小可控的实体提供带名称的合法选项；较大集合通过免费索引/查询工具定位并取得引用。

可以用明确的短句柄映射真实ID，映射绑定当前世界和实体类型。适配器严格检查世界、类别、存在性和可见性；不将任意名字猜成居民，不用模糊匹配自动选择接收者。实体已删除/状态已变时返回stale_reference与可重新读取的索引，禁止悄悄改成另一对象。

工具选择能力可按协议版本公开，但不通过只隐藏不够钱的动作来替居民决策。参数选项不能暴露模型、私有记忆或其他居民不可见实体。

## 调用校验与执行

所有线路输出先经过同一结构校验。错误字段、未知工具、类型错误、未知引用不会进入Runtime命令提交；只返回有限的结构化诊断。校验不更改模型的金额、接收者、目的地和内容，不截断后偷偷执行。

允许同一模型轮次返回多个独立工具调用。按原顺序处理，连续业务动作可以组合成原client.act的批次；遇到look、重新感知等边界时明确刷新状态。不能为了拆工具把多工具调用并行写入世界、改变转账顺序或擅自扩大每刻行动数。

原生模式无需为每个动作新增一次模型调用。轮次、每刻行动额度、look次数、叫醒次数、并发和token预算继续采用现有配置。若某线路不支持多个工具调用，调用方式变化可能影响可完成行动数，必须实测并说明，不能默默调大预算。

每个调用有独立结果，区分schema_invalid、reference_invalid、业务拒绝与成功。反馈明确“尚未提交 / 已提交且拒绝 / 已接受”。一次醒来结束前记录有限的未解决结构错误，下一次醒来不用依赖模型记住缺失的诊断；该摘要仅为兜底，主要约束来自协议与验证。

输入格式错误被拦截不等于模型已经完成有效行动；监控同时报告结构失败率和有效行动率，不能用没有进入引擎而掩盖无行动。

## 兼容与适用范围

第一阶段仅对显式启用的新工具协议使用类型化工具；旧客户端、外部Agent、旧act接口继续可用。网关不批量改用户模型配置或强制切换provider。

引擎仍接收原动作对象，原命令类型与历史回放算法保留。新的调用批次与感知时机必须在专项测试中与设计语义对照，不因“只是接口层”就宣称所有行为自然不变。

需要改动的模块：动作定义、runner工具生成/适配与循环、provider能力转换、HTTP/MCP的统一结构校验与协议说明。MCP不必第一批全部重构，可先保证生成定义一致和现有协议兼容。

## 验收

- 从真实审计抽取read.target、read.id、动作内look/end、函数式type等错误形状：新工具接口无需生成这些字段；对故意注入的非法形状，在世界命令提交前阻断。
- 类型化read_law正确生成原引擎read.law；验证费用、正文返回及地点/法律限制仍有效。
- 多工具同轮按序执行、不突破动作额度；done不进入命令日志；look继续免费且受原次数约束。
- 合法目标与金额由模型明确选择；非法引用不会被自动猜测、改名或替换。
- 对各provider进行mock请求schema及工具结果回填测试；严格生成成功只能由实际线路证据确认，不能以mock代替。
- 旧协议、旧世界、固定历史快照回放一致；新协议隐私测试不记录任意输入正文。
- 用自然调用观察格式失败和重复同类失败减少；不把schema正常、网络正常和游戏效果正常混为一项成功率。

## 保证边界

能保证不合协议的参数不进入游戏执行，并大幅减少需要模型记忆的接口细节。只有已确认支持严格结构生成的线路，才能提供相应结构保证。仍不能保证模型选对政策、对象、金额，或避免余额不足、无权限、法律否决、对象状态变化等业务失败。

此方案没有修改软件、生产接口、模型参数或居民行为。
