# ALTCHA 网站登录实施方案

依据：用户已要求实现 [可行性评估](../audits/2026-10-17-altcha-feasibility/REPORT.md) 中的方案。

## 行为与边界

- `LOGIN_CAPTCHA=altcha` 启用本站托管的 ALTCHA；`turnstile` 可切回旧服务；`none` 显式关闭。未设置时兼容旧行为：配置 Cloudflare 密钥则使用 Turnstile，否则不启用验证。
- 仅调整网站密码登录。注册、联系方式验证和微信原生登录的扩展需求仍按其各自设计处理。
- 前端使用固定版本的官方 external 构建、中文资源和 PBKDF2 Worker；服务端使用官方计算库。保留原始文件、MIT 许可和 npm 完整性摘要，不依赖运行时下载或新增 npm 安装步骤。
- 采用 PBKDF2/SHA-256、cost=1000、随机计数目标，`ALTCHA_MAX_COUNTER` 默认 2000，可在 500–20000 间调整。前端用两个 Worker；这些参数需要后续真实手机调优。
- 挑战有效期 180 秒，进程内最多 1000 个未消费挑战；签名密钥每次进程启动随机生成，不持久化。重启与切换实例后旧挑战失效。
- 发放挑战的 IP、全局限流及计算并发独立于登录预算；校验后原子删除挑战，密码失败也不得重用。无效答案不能提前耗尽账号预算。
- 登录按 IP / 全局限流 → 格式验证 → 验证并消费挑战 → 账号限流 → 密码校验执行。已有密码计算并发保护继续生效。
- 限流表增加容量上限与过期清理；容量不足拒绝新增键，不驱逐有效计数绕过限制。
- UI 自动启动验证，显示状态，失败可重试；每次实际登录提交后刷新挑战，关闭弹窗终止计算。服务不可用时不自动跳过验证。

## 实施与验收

1. 固定并核验上游资源，增加配置和挑战模块。
2. 增加缺失、篡改、过期、重放、并发、重启、容量、限流顺序的测试，并接入路由。
3. 接入登录弹窗与同源 CSP，覆盖 UI 生命周期和错误恢复。
4. 运行相关测试及全量测试，在真实浏览器验证官方组件求解、密码失败刷新、登录成功、关闭重开与同源资源请求。
5. 记录测试证据及启用/回退配置。用户已追加授权合并推送与生产部署，启用 LOGIN_CAPTCHA=altcha。

## 合入最新 main 的适配

- 同时接入独立登录页与账号弹窗，保留后续版本的首次联系方式补验和微信身份校验。
- 注册、首次补验和找回密码继续使用独立的 Turnstile 验证用途及发送额度，账号接口继续提供对应 site key；配置了该服务时，CSP 保留其来源。普通密码登录的 ALTCHA 路径不加载或调用 Cloudflare。
