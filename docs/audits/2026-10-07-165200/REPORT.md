## 一、软件中的法律是什么

| 层次 | 来源与修改方式 | 实际效力 |
|---|---|---|
| 自然律、守护律 | 平台引擎硬编码，居民立法不能改变 | 约束动作和规则权限，包括私域不可访问、退出与重订不接受 before 拦截、强制转账的生存底线等 |
| 宪章 | 多语言文字；居民以修宪级 `amend` 操作修改 | 宪章文字本身不被语义解释，也不自动成为其他法律的合法性审查标准 |
| 城法 | `propose` → `vote` → 到期计票 | 文字加 `rules`；文字没有可执行规则时只留下规范记录 |
| 立法程序 | 城法的特殊载荷 `procedure`，通过修宪级提案或重订改变 | 决定两类提案的资格、选民、权重、表决期和通过条件；免维持费 |
| 社群章程 | 管事直接设定，或社群成员多数表决 | 每社群一份；只在规定成员、账户和操作范围内有效 |
| 地点规则 | 个人主人设定；社群所有时按该社群程序决定 | 每地点一份；管此地动作和有门时的进入；城有地点没有独立地点规则 |

软件采用规则引擎自动执行，没有独立的法官、诉讼、证据审查、裁判和上诉执行链。`court` 是地图地点；不能因有“法庭”就认为已有司法模块。规格还将“契约（第三层私人规则）”列为未纳入范围。交易托管、遗嘱等属于各自的固定机制，不等于通用契约裁判。

法律的 `text`、宪章宣言与可执行规则可能不一致；目前没有解释自然语言后裁定规则违宪、冲突或无效的组件。`amend` 与 `procedure` 按载荷分类，不能识别普通规则在实际效果上是否架空公民权利。

## 二、制定与立法机制

### 城法流程

1. `draft` 可做类型、权限、引用、大小等校验并提供引擎读法；试算只收集当前状态下的意图。提案前不强制先 draft。
2. `propose` 校验标题、正文、规则或程序，两种载荷不能混用。含 `procedure` 或任何层级 `amend` 的提案走修宪级，否则走普通级。
3. 当前程序的 `proposers` 决定资格；`voters` 在提出时求值并保存名单，程序本身也复制保存。每人最多一个进行中的城提案，全城最多二十个。
4. 动作仍须支付能量、通过其他法律的 before 拦截。例如“只能在议会提案”来自遗法 l2，并非不可改变的物理限制。
5. 表决可改票，以最后一票为准。名单固定，计票时去掉已死亡或归隐者，沉睡者仍在分母内；权重表达式在计票时重新计算。若权重依赖财富或标签，表决期间其变化会改变最终票重。
6. 到期按提案顺序计票；通过后生成 `active` 法律，执行一次 `enact`，发 `law_passed` 和收件。`passed` 表示表决通过，不代表全部执行成功。
7. 新程序只取代它写明的类别。普通法律之间没有自动“新法优于旧法”；`basedOn` 只是来源关系，替换旧法须显式 `repeal`。废法不会自动退回已转移资金、恢复已设置变量或撤回已经改变的宪章文本。

### 社群、地点与恢复途径

- 社群 `steward` 程序：管事直接订章程、修改程序；`members` 程序：成员提出，固定当时成员名单，12 刻后按一人一票计票，参与至少一半且赞成多于反对即通过。每社群最多三个进行中的提案。
- 章程和地点规则整体替换，空数组为废除。社群地点提案生效时会复核所有权和静态引用；所有权已经变化时作废。
- 自动回退只检查“有人有提案资格”和“选民名单非空且求值成功”。连续三日不满足就把对应类别恢复为人类程序；`none:true` 明确不回退。
- 重订绕过当前表决程序和 before 拦截，3 日窗口、成功后 24 日冷却。门槛分母只算入城满 3 日的在世居民；签名分子只检查在世，存在下述 R1 风险。成功替换两类程序、作废其他进行中的重订，不废止普通城法，也不作废既有城提案。
- `secret:true` 只隐藏居民感知中的逐票列表；投票事件及公共观众接口仍公开投票者、选择、理由。这是规格明定的有限保密，不能把它描述成真正秘密投票。

## 三、执行机制与保证范围

时机包括 `enact`、`daily`、`monthly`、`before:动作`、`after:动作`、`on:事件`。before 仅允许拒绝和收费；其他时机可转账、设置变量、打标签、放逐、修宪、废法、征收地点等，具体受作用域白名单限制。

执行顺序通常为城法 → 所属社群章程 → 地点规则，各范围内按稳定顺序。日结先井产入库，再支付维持费，然后执行 daily/monthly，之后才进行代谢、腐坏、死亡等。持续规则每条每日一能量；不足时整份法律或章程停摆，程序法律免付，新生效当天视为已付。

**单条规则先完整求值、收集全部意图，再按顺序施行。** 同一条 do 里的 set 对后续表达式不可见，下一条规则才会看见变化。收集期错误丢弃该条规则所有意图；施行期的余额不足、越界、对象失效等则可产生部分付款或操作失败，其他操作继续。因此，不存在“一整部法律所有效果一起成功或一起撤销”的普遍保证。

规则效果不级联触发其他规则；从居民强制转出的能量受 10 的底线保护，但 fee 和自愿维持费不受此限。可执行规则能否达到治理目标，还取决于余额、资格、事件是否真的触发、执行顺序、整数取整和其他法律。

计算资源有两个版本：

- 旧执行路径：默认每次规则 2000 步，超限记录错误并丢弃该条；源码包含新执行器不表示旧世界已迁移。
- VM2：要求第二纪、premise ≥ 2、已记录 `ruleExecution.version=2`；正式入口检查计算成本与全城预留，命令在副本执行，容量错误整体不提交并保护暂停。人口等状态规模、规则总量、意图数和世界字节数都有边界。

VM2 保证计算容量，不保证公式不除零、账户资金充足或法规无冲突；其保护分支目前只处理 `CapacityError`，未覆盖 F1 的普通 JavaScript 异常。

## 四、确认的实现缺陷

### F1 / P1：地点被收回后，失效地点规则仍执行，打断日结

**条件：** 私有地点已有每日 `announce to:here` 规则；城法同日在 daily 中执行 `seize` 收回该地点。

**复现：** 日结预先收集全部规则集。城法先把地点变为城有、清空 `p.rules`，但后续循环保留旧地点规则集，仍执行宣告；宣告付款方从现有 owner 得到 `k:'city'`，账户层不支持该账户类型，抛出 `balanceOf: unknown account city`。

旧执行路径已进入 tick 12 且发生部分结算；VM2 保留 tick 11，但异常不是 CapacityError，所以 `paused` 仍为 false。若没有外部干预，VM2 下一次 tick 会再尝试同一失败结算。这里复现的是引擎异常和状态差别，没有声称 Node 进程退出。

Runtime 正常命令执行把异常包装为 `internal`；命令已先写日志，启动回放却直接调用引擎。因而还存在未被新快照覆盖的失败命令阻止恢复的风险；该恢复后果依据调用链，未在磁盘上重启服务验证。

**修复方向：** 执行每份规则集前复核其仍有效、仍是该地点当前规则且所有权符合要求；同时为不可恢复引擎错误建立完整命令不提交、明确停机和可重放的失败处理。不能只把 `city` 映射成公库，那会继续执行已经失效的私人规则。

**验收：** 收回地点当天不再执行其旧规则；旧/新执行路径和 after 场景均覆盖；失败命令重启回放行为确定。需对历史执行语义版本化，避免旧日志回放被悄悄改写。

证据：[预取规则集](/home/ctyun/projects/as4/src/e2/engine/rules.js:418)、[清空地点规则](/home/ctyun/projects/as4/src/e2/engine/rules.js:961)、[宣告付款账户](/home/ctyun/projects/as4/src/e2/engine/rules.js:754)、[异常保护边界](/home/ctyun/projects/as4/src/e2/engine/index.js:100)、[运行与恢复](/home/ctyun/projects/as4/src/runtime.js:74)。复现脚本 F1 两例。

### F2 / P1：法律收费没有实际冻结，动作内立法可花掉待付费用

**条件：** 城法规定 `before:rules` 收 20；居民当前能量 100，为自己的社群设定 enact，将自己能量尽量转入社群。

**复现：** 执行前验证 100 足够支付动作 2 加费用 20；先扣动作 2，enact 强制转账再把 88 转入社群，居民剩 10；框架最后再扣 20，居民最终 **−10，状态仍 awake，动作却返回成功**。两个执行器均复现。

这不是“fee 可突破生存底线”本身的问题：fee 确实是允许的自愿支出；缺陷是同一余额被先后承诺给两笔支出，最后支付超过剩余余额。VM2 的容量事务不会阻止这种业务上错误但正常返回的命令提交。

**修复方向：** 对 fee 建立真实预留/托管，并让动作内规则使用扣除预留后的可用余额；成功时结清，失败按定义回滚。避免只在最后拒付，因为动作和 enact 已经产生效果。

**验收：** 能量和旧币分别覆盖；设章程、事件钩子、收费接收方变化等组合下不能重复花费预留；守恒及余额不变量同时验证。扣费顺序影响居民可见效果，须保持历史版本并明确迁移。

证据：[执行前检查、apply 后扣费](/home/ctyun/projects/as4/src/e2/engine/actions.js:112)、[章程立即执行 enact](/home/ctyun/projects/as4/src/e2/engine/bylaws.js:35)。复现脚本 F2 两例。

### F3 / P2：一次性规则失败未进入法律执行结果摘要

**条件与复现：** 正式提出并通过一条 `enact set example = 1 / 0`。类型与成本准入通过；执行时有公开 `rule_error`，变量没有设置，但法律 `status=active`、提案 `status=passed`，`law.results=[]`，`law_passed.results=[]`，收件只通知通过。

表决通过而执行失败是既定语义；问题在于摘要把“失败”与“没有意图/没有 enact”混成空数组。仅查看法律通过回执、结果或收件时无法识别失败，enact 又不会在以后自动重试。此处并非完全无日志。

**修复方向：** 将收集失败以规则编号、错误码、阶段显式写入执行摘要；区分表决状态与执行状态，并向提案者提供失败提示，保留独立错误事件。

**验收：** 类型错误、除零、空条件、合法零操作能明确区分；接口字段兼容旧存档和客户端。若改变持久化事件/结果，也需验证回放。

证据：[失败直接 continue](/home/ctyun/projects/as4/src/e2/engine/rules.js:347)、[通过通知](/home/ctyun/projects/as4/src/e2/engine/legislation.js:260)。复现脚本 F3。

## 五、已复现的治理与语义风险

以下行为大多符合现有详细规格，应视为规则设计问题或公开文字不一致，不能直接按普通程序 bug 静默修改。

| 编号 / 优先级 | 条件与实测结果 | 影响与改进方向 |
|---|---|---|
| R1 / P1：重订分子、分母人口口径不同 | 城中一位已居住 3 日者，再注册一位新居民；门槛为 1，新居民自动签名即可把两类程序改为 none，原居民无需同意 | 更大城镇也可由足量新居民签名替代老居民赞成。统一分子分母的资格口径，决定名单何时固定；新增居民是否应能参与由治理规则明确 |
| R2 / P2：三分之二与 667‰ 不相等 | 2 赞成、1 反对的默认修宪提案被否决 | 遗法正文承诺“三分之二”，执行要求 66.7%。现有测试明确保留第一纪兼容。若目标为精确三分之二，可用 `yes*3 >= (yes+no)*2`，但应经居民修法或明确版本迁移；否则纠正文案 |
| R3 / P1：禁止规则错误后放行 | 同一 before 规则先写无条件 deny，后写 fee 金额 `1/0`；整个收集失败，say 动作成功 | 任何依赖该条禁令的权限边界都可因公式/引用错误而失效。属于明定的错误后放行策略。应在 draft 明显展示风险；如需错误时拒绝，必须单独定义治理语义，保留退出/重订权 |
| R4 / P1：程序实际瘫痪不触发回退 | 通过重订安装 `decide='1/0>0'`；连续三次每日健康检查保持正常计数 0；立即重订恢复又被 cooldown 拒绝 | 资格与选民都存在，但所有表决都会在决定阶段报错并否决。健康诊断应至少报告权重/决定运行错误和恢复受限，是否扩大自动回退条件需明确决定 |
| R5 / P1：旧修宪提案覆盖重订 | 两名居民先为关闭两类立法的提案投赞成；随后共同重订恢复人类程序；旧提案仍 open，到期通过后两类又变 none，重订仍在冷却 | 重订并不清除旧程序快照下的修宪提案，恢复可能短暂失效。明确重订对在途修宪案的效力，可选择作废、重新确认或程序代次校验；不能擅自把所有普通法案一并作废 |

## 六、还会造成“不执行/执行不合预期”的正常机制

1. **文字法不执行。** 只有自然语言禁令、或只修改宪章正文，不会自动限制动作；程序也不验证文字目的是否与规则一致。
2. **未废旧法会叠加。** basedOn 不替代；重复配给、重复收费、变量覆盖均可能是多法共同作用。不存在通用冲突裁决器。
3. **维持费不足使禁令与权利规则一起停摆。** 如公民授予的事件规则当时停摆，之后恢复不会自动重放历史入城事件。事件型、一次性规则没有补执行机制。
4. **试拟不是完整执行模拟。** preview 不实际施行、不覆盖 before/after 的具体动作、不模拟未来人口或资金；不同规则之间也不会先把前一条结果施行到副本。可能漏掉施行期错误，也可能把执行时本可由上一条初始化的变量报告为错误。单条成本合格还不代表正式入口的全城合计成本合格。
5. **金额不保证足额。** transfer 可部分执行，share 整数均分且余数留在来源账户；each 依次转账时先到者优先。把 each 改成 share 会改变居民政策，不能作为无差别“优化”。
6. **同规则内变量有旧值。** 先 set 再引用该变量仍读取执行前值；应由法案作者明确使用分条规则或内联表达式。
7. **账户/成员/事件都有寿命。** 被引用居民离场、社群解散、对象消失或不在作用域，都可能让规则报错或具体操作失败。生命周期变化必须纳入法案测试。
8. **全城变量共用。** 城法可以更改其他城法依赖的变量，64 个槽位满时 set 可失败。没有法律专属命名空间或变量写入权限；这是治理自由与干扰风险的取舍。
9. **保护暂停也会停止法律执行。** VM2 达到容量上界时冻结整个世界是 ADR-0004 明确选择，不能误报成“规则被跳过”；需要平台扩容和检查。未迁移世界仍有旧 fuel 风险。
10. **公开协议仍描述固定 2000 步。** VM2 世界需要按实际版本显示容量保障，避免居民把旧界限当成当前事实；反过来也不能用新版宣传掩盖未迁移世界的旧行为。
