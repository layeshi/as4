根因证据：事件 seq 1327、tick 48、law l10、rule 1，`rule_error / type / /需要整数，得到 null`。

《配给兑付与保底法》在同一条 daily 的 do 中先 `set ncit`，随后用 `var.ncit` 计算 perhead，继续 set cap，最后转账。现有语言是先在旧状态上收集全部操作意图，再统一施行；前面的 set 不会立即对后面的求值可见。`ncit` 尚不存在，于是计算失败，整条规则包括所有 set 都丢弃。源井入账发生在此前，不受影响。

这符合 SPEC-E2 §7.5 的现有执行语义；应区分“居民法律写错”和“引擎未按规格执行”。平台的反馈丢失和提示不足使此类错误难以被居民识别。

按该法律文字意图，该日有 12 位公民，618×60% 向下取整为 370，每人应发 30，共 360。若这笔配给正常执行且其他项目保持相同，该次日终公库应为 642，而非 966；差额为 324，另 36 因公库少腐坏而抵消。这是单次结算的反事实计算，不是已经补发。

## 3. 已确认的软件缺陷与运行质量问题

### P1：动作结果没有进入模型下一轮输入

`runner/agent.js:275` 用 `summarizeResults()` 保存结果；`runner/render.js:337` 仅保留动作名、外层 ok、代价，丢弃 `data` 和错误 hint/issue 明细。

- draft 外层执行成功，只代表“已进行试算”；内部校验失败或 preview 错误都可能仍被显示为 `draft ✓`。
- read 返回的文献全文、铭刻全文和法律数据没有进入模型上下文。read 本身没有把这些正文另投进收件箱。
- 线上累计出现 53 次 draft、58 次 read；不是说每次都业务失败，而是这些动作返回的重要详情没有经该运行器反馈给模型。
- 真实命令重放发现 tick 32、33、40、42 的 draft 返回 `data.ok=true` 且 preview 含 null 运算错误；运行器只给成功摘要。
- 两轮 runAgent 的本地集成复现验证：服务返回了真实错误和真实典籍正文，第二轮模型消息只有 `draft ✓`、`read ✓`，不含错误详情和正文。

优先修复反馈链，保留结构化结果和足够详细的诊断；长文需有可继续读取的截断机制。不要替居民修改其行动。

### P1：试算成功状态与运行预览错误混在一起

`src/e2/engine/actions/politics.js:153` 在静态校验通过后写死 `ok:true, errors:[]`；`previewRules()` 将运行错误放进 preview 数组。这不是“所有验证都通过”。建议明确区分静态校验成功、预览成功和警告，给出具体 rule/op 路径，并解释同一规则 set 的可见性。

### P2：人均配给指标漏计，可能误导经济判断

`src/e2/engine/rules.js:674` 只记录每日从城公库执行的第一笔 share；each+transfer 不计入，多次 share 也不合计。

- tick 24 实际每人收到 58，指标只有 29。
- tick 36 实际每人收到 30，指标为 0。
- tick 48 的 0 才是真实停发。

指标改进需要先明确“配给”的识别方式；不能把所有转账都算配给，否则修缮补贴也会混入。可以增加公库每日入账、分发、补贴、维护、腐坏及实际领取统计。

## 4. 游戏规则是否完善

已有账本、能量底线、法律维护费、投票、规则执行预算、只读内心边界等机制；本次未发现账本失衡。仍有如下已经发生或可复现的问题：

1. **配给法替换不自动发生。** l7 写了 basedOn=l3，文字说“取代”，但 basedOn 只记录来源，不撤销旧法。tick 24 确实双发。居民后来通过 l9，在 tick 27 撤销 l3。应向居民明确“参考”和“替代”区别，预览同类持续规则并行的影响；不要默认自动废法。
2. **护井门槛量纲错误。** l8 文字为低于 80%，表达式却是 `city.wellCondition < 800`；该字段使用 0–10000 基点，因此实际低于 8% 才生效。合成世界在 79% 时汲取 3 成功，违背其文字意图；应为 8000。
3. **护井补贴范围错误。** l8 的 after:repair 未检查 `result.target == 'well'`，修图书馆也能领公库补贴，本地已复现。线上已发出的六次补贴目前都是修井，尚无实际利用证据。
4. **补贴上限表达不准确。** `actor.repairedToday <= 10` 是“当日累计修缮投入”限制，非“累计补贴不超过 5”。一次修 12 会完全得不到补贴，而非领满 5；其他建筑修缮也占这个计数。
5. **保留金 50 不是全局保护。** 即使 l10 正常运行，它只限制该配给规则；其他补贴、维护、法律转账仍可动用余额。文字“永远保留”强于代码保证。
6. **规则语言对 Agent 的说明不足。** 系统提示未明确同条规则先收集后施行、基点与千分比的区别、basedOn 不替换，以及错误预览不代表通过。大量静态错误恰好涉及 city 前缀、treasury 账户与余额、变量引用等。

语义收集方式是已有明确规格，不宜在修复反馈问题时顺便改为逐操作修改世界：那会改变旧法律含义和历史回放。
