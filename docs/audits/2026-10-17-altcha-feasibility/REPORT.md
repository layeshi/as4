# ALTCHA 与登录限流的可行性评估

日期：2026-10-17（北京时间）。

## 结论

**有条件可行，适合作为当前单进程网站的免费、自托管登录防滥用方案。建议采用“ALTCHA 开源组件 + 调整后的登录限流 + 一次性挑战管理”，不建议仅替换前端控件和校验函数就上线。**

收益是登录验证的脚本、挑战生成和答案校验均可在本站完成，去掉 Cloudflare 验证链路的外部依赖。网站本身的访问延迟仍然存在；本次没有测量国内移动网络或生产服务器上的端到端速度。

免费 ALTCHA 的基础机制是工作量证明：浏览器完成一段计算，批量请求需要承担相应计算成本。脚本也能完成计算，因此不能把通过 ALTCHA 当成真人身份的证明，不能据此承诺与 Turnstile 相同的风险识别能力。ALTCHA 官方明确区分免费的 Widget / Libraries 与付费 Cloud / Sentinel；本建议使用 MIT 许可的开源组件，费用仍包括自有服务器资源和维护。

## 评估范围与现状

检查本地工作区的登录路由、限流器、密码校验、前端弹窗、CSP 和相关设计记录；核对官方文档和 npm 发布版本；在临时目录与临时账户数据中进行隔离实验。未修改应用代码、未连接生产服务器、未部署替换。

| 项目 | 已确认事实 | 对方案的影响 |
| --- | --- | --- |

## 本地验证结果

### 现有账号限额可以被无验证令牌请求耗尽

使用项目现有 HTTP 测试启动器创建临时服务及临时账号，配置 Turnstile 后，从一个测试 IP 向该账号提交 15 次不含令牌的登录请求：全部返回 `turnstile_required`，没有进入密码校验。随后模拟另一个 IP 的合法登录，在到达人机验证函数之前就收到 `429 rate_limited`。

这是当前实现已经存在的问题，ALTCHA 不会自动修复。建议先做 IP / 全局资源限流，验证并一次性消费挑战后，再扣除账号尝试额度并校验密码。账号额度也需要并发安全；不能简单改为在异步密码校验结束后才无保护地累计失败次数。

另外，隔离调用确认新的限流器实例会放行此前已经耗尽额度的用户名；在同一窗口插入 10001 个活跃键后，Map 仍保留 10001 个键。要给新增挑战状态设置硬容量与过期回收，不能把当前的清扫阈值直接作为容量保护。

### 官方库可本地校验，但底层函数不负责防重放

核对到 npm 发布的前端 `altcha@3.4.0` 和服务端 `altcha-lib@2.6.0`。从官方 npm tarball 在临时目录加载后者，未运行包安装脚本。

以下为本机 macOS arm64、Node.js v22.14.0 的单次能力验证，采用 PBKDF2/SHA-256 及官方支持的双 HMAC 签名方式。它不是浏览器、手机、生产服务器或大陆网络性能测试，也不是生产参数建议。

| 用例 | 结果 |
| --- | --- |
| 轻量实验参数：cost=1000、counter=400 | 生成约 1.85 ms，求解约 66.94 ms，校验约 0.35 ms |
| 文档示例范围下限：cost=5000、counter=5000 | 本机 Node 求解约 3525.76 ms |
| 正确答案 | 通过 |
| 修改已签名的用途字段 | 拒绝 |
| 已过期挑战 | 拒绝 |
| 同一答案重复调用底层 `verifySolution` | 再次通过 |
| 同一答案同时调用 8 次底层校验 | 8 次全部通过 |

重复通过符合底层函数的职责边界；官方另提供 Store 接口用于记录已使用挑战，并说明需要原子的 `setIfAbsent` 才能防止并发重放。当前项目使用原生 HTTP 路由，必须在接入层落实这项控制。

## 建议实施方式

1. **全部资源同源托管。** 固定并核对前后端版本，保留许可文件；脚本、样式、语言资源、Worker 和挑战接口均由本站提供。使用 external 构建适配现有 CSP，避免依赖海外 CDN。
2. **新增挑战发放接口。** 由服务端决定算法、难度、有效期和用途；建议从 2–5 分钟有效期开始验证。随机挑战须有签名，令牌仅用于相应操作，不接受客户端降低难度或更改有效期。
3. **挑战只能消费一次。** 单进程可维护有硬容量、定期清理的“尚未消费挑战表”；有效签名与答案通过后，原子消费，再进入密码校验。密码错误也需要新挑战。重启后拒绝旧表中已不存在的挑战，避免只清空“已使用表”却继续接受旧签名所带来的重放窗口。表满时限流，不能淘汰仍有效的已用记录后继续放行旧令牌。
4. **调整限流顺序。** 请求大小 / 格式校验与 IP、全局资源限额在前；有效挑战的一次性消费在中；账号尝试额度和密码校验在后。挑战发放、校验均需独立容量与并发限制，沿用现有密码计算并发上限。真实 IP 的可信代理配置需要上线时复核。
5. **按终端实测选择难度。** 打开登录弹窗时可以后台启动计算；过期、密码错误、请求失败后提供重新验证，关闭弹窗释放 Worker。可以把普通手机大部分挑战在约 1 秒内完成作为首轮调优目标，但需同时评估攻击计算成本，不能为追求快而把挑战设成近乎无成本。
6. **保留可控回退。** 明确配置使用 Turnstile 或 ALTCHA，并保留切回能力。ALTCHA 加载或校验失败时提示重试，不应自动绕过验证。上线记录验证耗时、失败率和 429 数量，不记录密码、完整令牌或签名密钥。

单进程原型不必为了这项替换立即引入 Redis。若将来多进程或多服务器共同处理账号登录，账号限流和挑战消费状态都需要共享与原子操作；当前账户 JSON 文件也已有单进程限制。

## 适用范围与上线判据

- 普通网站密码登录：满足以上条件后可采用，能去除 Cloudflare 验证依赖，提供基础的批量登录成本约束。
- 大规模分布式撞库、密码已泄露后的少量精准登录：免费静态 PoW 的保护有限；管理员等高权限账号的额外身份验证应独立评估。
- 注册、找回密码和短信发送：本次不作整体替换结论。现有联系方式方案还要求发送频控、每号码/邮箱限制和全站短信每日硬上限，ALTCHA 不能替代这些规则；如要更换其 Turnstile，需同步更新设计并单独验证费用滥用风险。
- 微信小游戏原生登录：不能直接嵌入网页 Web Component；继续按已确定的微信服务端身份验证方案处理。微信内置网页浏览器的兼容性需真机验收。

上线前至少验证：合法登录；缺失、篡改、过期、跨用途和重复令牌拒绝；并发提交只消费一次；密码失败后旧令牌失效；服务重启和状态容量满时不绕过验证；无令牌请求不消耗账号额度；挑战请求洪泛不挤占世界运行；真实代理 IP 与限流行为；Android / iOS / 微信网页浏览器的加载、计算及弹窗重开；断开第三方服务访问仍能完成本站验证。

**本次完成的是代码级可行性与隔离机制验证。端到端速度、真实手机兼容性、生产资源占用和迁移后业务回归仍属于上线前验证项。**
