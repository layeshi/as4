# 批量会话生成与世界提交版本衔接修复

日期：2026-10-27。对应多核资源适配功能的上线验收修复。

## 问题与证据

首批实现 `9c55e5f` 的合成 tick / 查询基准及单居民会话测试通过，但没有覆盖多位居民同时唤醒的启动负载。首次上线后的自然运行记录显示：18 次新唤醒中，17 次为零轮次，只有一位居民进入模型调用。在本地真实 worker 和 ordered inline 模式均复现了批量 `wakeCore()` 仅首个成功、其余返回 `compute_busy`。

原因是会话队列只按居民串行。不同居民会同时在相同旧 `commandN` 上生成内容，而每次计费本身都改变世界版本；首条命令提交后，其余命令的 `expectedVersion` 检查因此拒绝。保留版本检查是必要的，不能通过移除检查发布过时内容。

发现后已正常停止候选程序，在当前数据副本上验证旧版本恢复兼容，再仅切回旧代码。没有用发布前备份覆盖数据，已提交的 6 条新命令保留至 `commandN=19546`，居民、账户及运行器配置保留。完整发布和恢复证据由服务器受限备份目录保存。

## 修复行为

- 每个 Runtime 共用一条有界会话 FIFO。唤醒、查看及行动的会话更新有序完成；模型网络调用在队列之外，模型并发、预算和行动频率仍由原配置控制。
- 开始生成内容前等待世界命令队列完成，并循环核对 tail 身份；观察者在提交时插入的新命令也必须先完成。稳定版本检查与同步生成、提交之间不插入 await。
- 保留 `expectedVersion`、资源预算和提交前权限复核；会话实际开始时额外复核请求权限与运行时关闭状态，覆盖直接返回已提交回执的重试分支。
- 等待从入队开始最多 30 秒。超时后返回繁忙，不再生成内容、创建唤醒或收费；尚未退出串行链的过期条目继续占用队列名额，防止前置任务阻塞时无限积累。
- 旧代币世界的动作已经持久化后，附加收件计费若遇繁忙，只暂缓附加文本并返回已提交动作结果，避免调用者误以为动作未提交而重试。

## 验证

已先复现失败，再验证修复。5 项新增回归覆盖：

1. 不同居民批量唤醒和查看，含已排队 tick、提交观察者再插入 tick；真实 worker 和 inline 模式均完整执行。
2. 会话等待世界队列时仍受任务数上限约束。
3. 排队超过 30 秒后不延迟执行、不收费、不创建唤醒。
4. 排队中的同请求重试，在返回缓存回执前复核它自己的授权。
5. 旧代币动作提交后，附加计费繁忙仍返回该动作结果。

上述 5 项全部通过；独立复核另行运行同样回归，5 项通过、0 失败，未发现本轮新增 P1/P2。Node v24.16.0 全量回归 2,177 项通过、0 失败、1 项因外部冻结世界副本未配置而跳过。详见 [结构化结果](2026-10-27-batched-session-validation.json) 和 [完整日志](2026-10-27-batched-session-complete.tap.gz)。服务器专项及最终上线结果另记部署记录。
