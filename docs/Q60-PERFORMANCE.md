## 假设与证据

1. **重复历史表枚举是实际热点**：若成立，CPU profile 会显示较高键枚举成本，命令内复用后 CPU 时间应下降。profile 中 buildPerception 约占 77%，历史表过滤约 27%，键枚举约 17%，地图路程约 7%。命令内复用后，首次交替比较 CPU 时间由约 145 秒降到 122 秒，支持这一假设。
2. **前序用例造成显著性能变化**：若成立，同一文件完整运行应显著慢于单项。此次目标用例在完整文件中约 140 秒，与带 profile 的冷启动诊断相近，没有复现两倍差异。
3. **内存交换或调度压力解释历史 292 秒**：若成立，失败运行应有资源或调度证据。此次各对比测量均无重大缺页、无交换，CPU 时间接近或超过墙钟时间；未捕获历史失败时的等价资源样本。不能将历史差异全部归因于机器负载，也不能宣布性能在任意负载下稳定。

基线也超过门槛，而当前分支生成完全相同结果且更快，因此本次受控测量没有观察到 P4 对该旧世界负载的性能回退。新的完整验收已通过并取代历史最后一次失败作为当前验收状态；原失败记录保留，不以单项通过替代完整验收。

## 实现边界与验证

沿用已存在且有差分测试的 `withRecordQueries`：第二纪的普通同步命令只共享各历史表的键枚举。编号表的新增由对应已有 ID 计数器驱动重新枚举；记录值和状态始终现读，不缓存过滤结果。词典插入显式失效。正常返回、抛错及嵌套命令都会清理或失效作用域；未进入该作用域的查询仍直接枚举。索引只在 WeakMap 中，不进入世界或快照，不改变随机流与枚举顺序。现有受保护命令的执行路径不扩展缓存。

新增真实引擎命令边界的测试覆盖：同命令内编号插入、状态关闭、命令间直接写入、异常退出，以及 define 后同命令再次构建感知。已有 collections 与感知测试合计 26/26 通过。优化后第二轮约 116 秒，与第一轮约 113 秒接近；相对交替回测的优化前版本约 136 秒，墙钟改善约 15%–17%，CPU 时间改善约 14%–16%。完整 npm test 已完成：1454/1454 通过、0 跳过，Node 报告总耗时 1462714 ms。三个冻结世界回放、premise 0/1/2 黄金样本、P4 60 世界日守恒与回放通过；测试后 test/fixtures/p2 与 test/fixtures/p4 没有 Git 差异。完整日志为 `/tmp/as4-q60-full-test.log`。完整验收中的目标用例约 142 秒，比单独测量更慢且接近门槛，应保留此波动与 60 秒目标未达的限制，不能宣称任何运行条件下都达标。
